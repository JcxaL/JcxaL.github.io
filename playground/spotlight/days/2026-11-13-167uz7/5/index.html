data-state inspector

component · headless

The component is the markup.
The script just listens.

Four unrelated widgets below share one 60-line binder. It never creates an element and never sets a style — it reads data-slot to learn the parts, and writes data-state so the stylesheet can do the rest. Keyboard behaviour and ARIA come for free.

1 · tabs

Every element names itself. tabs-list, tabs-trigger, tabs-content — the binder queries for them inside the root and never looks outside it.
The active trigger and its panel both get data-state="active". That attribute is the entire public API between behaviour and appearance.
← and → move between triggers, Home and End jump to the ends, and roving tabindex keeps one stop in the tab order. Try it. 
<div data-slot="tabs" data-default-value="parts">
  <div data-slot="tabs-list">
    <button data-slot="tabs-trigger" data-value="parts">Parts</button>
  </div>
  <div data-slot="tabs-content" data-value="parts">…</div>
</div>

2 · accordion

A class says how something looks. data-state says what it is doing. One of those two belongs in a behaviour library, and it isn't the first.
The content is a grid with grid-template-rows: 0fr, flipped to 1fr when open. The browser interpolates the track, so nothing has to measure scrollHeight.
Change data-type="single" on the root to multiple. The markup is the configuration.

3 · dialog

Nothing here is a framework

Focus moved into the dialog on open, Escape closes it, Tab is trapped inside, and focus returns to the trigger on close — all from the same attribute scan.

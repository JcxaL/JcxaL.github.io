The moment before it opens

The toggle event tells you a panel opened. beforetoggle tells you one is about to — while it is still display: none, before a single pixel has been committed. That is the only frame in which you can aim it at the button that summoned it, or decide it should not open at all.

1 · Aimed at whatever opened it

One popover, four invokers. On beforetoggle the handler reads event.source, measures that button and writes the position and transform-origin — so the sheet grows out of the right corner every time, with no flash of a wrongly-placed panel.

Positioned before paint

Opened from —. The origin was set during beforetoggle, one event earlier than toggle would have allowed.

2 · An opening you can refuse

beforetoggle is cancelable on the way open. Flip Guard to refuse in the panel and this one never appears — no flicker, no opening then closing.

It got through

The guard was open, so preventDefault() was never called and the state change went ahead.

On the way closed the event is not cancelable — the browser will not let a page trap you inside a popover. The log shows cancelable for every event it records.

3 · An accordion that hears the change

Three <details>. Whichever one is opening closes the others, driven by the toggle events rather than by clicks — so it keeps working for keyboard, for find-in-page expansion and for anything that sets open in script.

What fires, and in which order
For a popover: beforetoggle (closed → open), then the browser shows it, then toggle. Both carry oldState and newState.
Why not just listen for clicks
Because the state can change without one — showPopover(), the Escape key, a light dismiss, find-in-page opening a closed section. The event is the truth; the click is one of several causes.
What event.source gives you
The control that initiated the toggle — the button with popovertarget, or the commandfor invoker. It is how a single shared panel knows which of four buttons it belongs to this time.

The Scrollspy Rail

A floating glass rail tracks your position through a long document. Instead of the active label just flipping state, a pill physically springs to it — overshoot, wobble, settle — like a magnet finding its section. Scroll the article, or click a label to jump.

01 / 06

1Orientation

Every long-form document needs a way to tell readers where they are without forcing them to scroll back to a table of contents. The scrollspy pattern solves this by watching the viewport and mirroring the reader's position in a persistent piece of navigation chrome — usually a sidebar, sometimes a top bar.

The trick is doing it in a way that feels alive rather than mechanical. A label that simply toggles a CSS class on and off reads as a status light. A label that a pill travels to reads as something tracking you, in a good way — the interface feels responsive at a level below conscious attention.

2The mechanism

Under the hood this rail uses a single IntersectionObserver watching all six sections at once, with root margins biased toward the vertical center of the viewport. Whichever section reports the largest visible ratio near that center line becomes "active" — not simply the first one that intersects at all, which tends to flicker between adjacent sections during fast scrolls.

Once the active section changes, the rail doesn't re-render anything. It just updates one target index. A separate render loop, running independently on requestAnimationFrame, reads that target and animates a floating pill element toward it every frame using position and velocity, not a CSS transition.

Decoupling "what's active" from "how the pill moves" is what makes the click-to-jump case work cleanly too — the target can change instantly on click, while the pill keeps animating smoothly even as the page is still mid-scroll underneath it.

3Spring, not easing

A CSS transition: transform 300ms ease-out would get the pill from A to B, but it would arrive and stop dead — no sense of weight. Instead this demo runs an actual damped-spring integrator each frame:

force = -stiffness × displacement - damping × velocity, then velocity += force × dt, then position += velocity × dt. Two numbers control the whole feel: stiffness (how hard it's pulled toward the target) and damping (how much that pull is resisted). Low damping relative to stiffness produces the overshoot-and-wobble you can feel when you drag the sliders in the panel and then click around the rail.

Try dragging damping down toward 4 and stiffness up toward 400 — the pill will noticeably ring past the target before settling, closer to a plucked string than a slide.

4Keeping it at 60fps

The pill is moved with transform: translateY() exclusively — never top, never re-measuring layout inside the animation loop. All label positions and heights are measured once up front (and again on resize, throttled), cached in a small array, and the render loop only ever reads from that cache plus the spring's current numbers.

The IntersectionObserver callback itself does almost no work — it just compares intersection ratios and writes one integer. That keeps scroll-driven updates cheap even on a mid-range phone, where the horizontal strip variant below has to keep up with fast swipes.

5Collapsing gracefully

A vertical rail pinned to one edge works fine on a wide viewport, but on a phone screen it either overlaps content or has to shrink until it's unreadable. Below 640px this demo swaps the rail for a horizontally scrollable strip pinned to the top of the viewport, with the same spring-driven pill running in the perpendicular axis instead — translateX rather than translateY, sized to each label's actual width.

Tapping a label in the strip auto-scrolls the strip itself to keep the active chip centered, in addition to scrolling the article. Nothing about the underlying spring math changes — only which axis and which cached rectangles it reads from.

6Where the idea comes from

The underlying behavior — watching scroll position and syncing a navigation indicator to it — is the core job of lightweight scrollspy libraries like fsegurai/scrollspy on GitHub, which focuses purely on the detection-and-highlighting logic and stays unopinionated about how the "active" state is rendered.

This drop takes that detection idea and pushes hard on the rendering half: instead of a class toggle, the active state drives a small physics simulation. Everything here — markup, spring integrator, resize handling, mobile strip — is written fresh for this gallery rather than reusing any of the original library's code.
